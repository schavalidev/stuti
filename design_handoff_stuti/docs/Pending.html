Push notifications that survive a closed browser

Today's bell buttons (sandhyā, pañcāṅga digest) only ring while a Stuti tab is open — stuti-nudge.js arms a plain setTimeout against the browser's own clock. A phone with the tab closed, or the browser killed to save battery, hears nothing. Fixing that needs a server standing between the almanac and the device, because only a server can hand the OS a wake-up call in advance.

What is already in place: stuti-push.js stores a device's push subscription (endpoint + keys) in localStorage and exposes subscribed() — the client half of the handshake exists, unused.

What is missing, in order:

  1. A subscribe call — PushManager.subscribe() against a VAPID public key, wired to the existing bell taps and the Settings reminder toggles, replacing the local Notification.requestPermission() path for anyone who grants it.
  2. A small backend (a cron-triggered function is enough — no always-on server needed) that, once a minute, computes which subscriptions have a cue due in the next window: sandhyā junctures per subscriber's saved place, the daily digest at their chosen hour, tithi nudges. The almanac math is pure and already lives in stuti-panchanga-engine.js/stuti-muhurta.js; the backend needs the same formulas (or to call the same JS via a small Node runner) plus each subscriber's place and prefs, which today live only in the browser's localStorage and would need to move to a real store.
  3. A send step using web-push (or the provider's REST API) with the VAPID keys, POSTing the payload to each due subscription's endpoint.
  4. A service worker push event handler to show the OS notification when the payload arrives with no page open, and a notificationclick handler to focus/open the app — mirroring what stuti-nudge.js's post() already does for the in-tab case.
  5. A place to keep subscriptions and preferences server-side (endpoint, place, sandhyā toggles, quiet hours, digest time) — today all of that is localStorage, which no server can read.

Scope, not a build: this needs a real backend decision (which host, which store) before any of it can be written. It is item 3 of Stage 2 in the launch tracker and begins after the four-week launch month.
