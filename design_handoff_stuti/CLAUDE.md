# Akshara / Stuti — project notes

## Working rules
- **The project root is the only copy of the app.** There is no handoff folder to mirror. `REPO-LAYOUT.md` maps root files onto the repo `schavalidev/stuti`; when a new root file is added, add it to the map if the tie-break rule would misplace it.
- **Register — the reader is an elder, not a scholar.** Short sentences. Plain words. No essayistic register: no piled clauses, no dashes holding a second thought, no clever turn at the end of a line. Respect is not optional — every person named in a rite is owed the same dignity, and nothing about a rite, the dead, or a family relation is ever a place for wit. No ambiguity: say the thing plainly or say nothing. Formal, but not casual and not stiff. **Never explain to the reader what they already know** — a screen that says "print cannot know your family" is both obvious and faintly insulting. Say what the screen does, not why it needs to exist. No preaching, no reassuring, no justifying.

  The case that produced the rule: a tarpaṇa text was introduced with "…the wife, the son, the daughter, the teacher, **the man who once lent you money** — each receiving three double-handfuls of sesame water." The list is a list of the dead being offered water. It is not a place for a punchline. It now reads: "Water is offered to thirty-three: father and mother, their parents and grandparents, wife, son, daughter, brother, sister, teacher, and others."

- **Update `Changelog.html` at the end of every run.** Add to the current version's section, or open a new one when the work starts a new arc. Follow the house voice: name the cause, not the symptom; entries are prose, not bullet dumps of file names.
- **End every run with a handoff summary** — a short block the user can paste into a new chat: what changed, what's pending, and any context a fresh session would otherwise have to rediscover.

- **Every language's string is written in that language, as one whole sentence.** Never assemble a line from fragments joined by a space, a middle dot, or a variable in English word order — write the full sentence per language with a `__` placeholder for the number, and let each language put the number where it belongs. Never translate the English word for word: `కర్మ అడిగే పేర్లు` is English grammar in Telugu letters; `కర్మకు కావలసిన పేర్లు` is Telugu. A string that reads oddly aloud to a native speaker is a bug, and ambiguity in a rite's interface is never acceptable — say the thing plainly in the reader's own language or say nothing.

  The case that produced the rule: a register header was built as `{count} + "వ్రాసినవి" + " · " + "ముప్పై మూడులో"` and rendered "1 వ్రాసినవి · ముప్పై మూడులో" — three fragments in English order, meaning nothing. It now reads "ముప్పై మూడులో 1 పేరు వ్రాశారు".

## Design preferences
- **No italics, ever.** Always use regular (upright) font. This applies to IAST/transliteration, glosses, captions, notes — everything. Do not use `font-style: italic` or `fontStyle: "italic"`.
- **One calendar, everywhere — and it wears the app's colours.** Any screen that shows a month, picks a date, or seeds a rule from a day reuses the house calendar in `stuti-calendar.jsx` — the `cal-grid` / `cal-wd-row` / `cal-cell` markup with its day number, moon phase and vrata marks, `sel` and `today` states. Never build a second month grid, and never use a bare `<input type="date">` for a date the rite cares about: a date in this app is a tithi, a browser date picker cannot show that, and it paints itself in system blue against every token in the design system. The house date field is `HouseDate` in `stuti-datepick.jsx` — use it for every date. Every cell, mark and state takes its colour from the app tokens (`--gold`, `--accent-soft`, `--accent-ink`, `--ink`); no system blue and no hard-coded colour, anywhere a calendar appears. Where a screen needs less, it uses the same grid with fewer marks — not a different one.
- **No native browser tooltips.** Never put a `title` attribute on a control. It renders a dark OS box outside the card that ignores every token in the design system. Use `aria-label` for the screen reader and put the words on the screen if they need to be read.

## Typography — how to avoid font-detective sessions
- **All font choices go through the CSS tokens** (`--font-ui`, `--font-display`, `--font-deva`, `--font-telugu`, `--font-deva-serif`, `--font-telugu-serif` in `stuti.css`). Never hard-code a family name in a rule or a JSX `style={{ fontFamily }}`.
- **Known inline-family exceptions** (they beat every stylesheet rule — check these FIRST when a font "won't change"): `stuti-sky.jsx` (sandhyā plate title + till, greeting), `home-redesign.jsx`/`stuti-flow.jsx` end-marks. If more are added, list them here.
- **Alias trap:** `'Surasans02 Regular'` is one Regular.ttf registered across weight 300–700 — every weight renders as Regular. For a real bold, use the `'Surasans02'` family (has true faces at 300/400/500/700). Nothing heavier than 700 exists in any project font.
- **When diagnosing, don't guess from CSS** — probe the live element's `getComputedStyle(el).fontFamily/fontWeight` plus `document.fonts.check()` in one shot; inline styles and `:is()` specificity make source-reading unreliable.
